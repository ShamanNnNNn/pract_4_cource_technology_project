# Application Management System

Backend-приложение для управления заявками. Пользователи могут создавать заявки, отслеживать их состояние, менять приоритеты и просматривать статистику.

Проект разрабатывался как практический Java Backend-проект: хотелось не ограничиваться простым CRUD, а реализовать полноценное приложение с авторизацией, работой с базой данных, тестированием и автоматизацией сборки.

## Возможности

- Создание, просмотр, редактирование и удаление заявок.
- Авторизация пользователей с помощью JWT и Refresh Token.
- Разграничение доступа на основе ролей (RBAC).
- Отслеживание статусов заявок и сохранение истории их изменений.
- Установка приоритетов и сроков выполнения.
- Фильтрация, сортировка и пагинация.
- Статистика по заявкам за выбранный период.
- Документация API через Swagger UI.

## Как устроен проект

В основе приложения — многослойная архитектура:

- `Controller` — принимает HTTP-запросы и возвращает ответы.
- `Service` — содержит основную бизнес-логику.
- `Repository` — отвечает за взаимодействие с базой данных.
- `Entity` — описывает сущности приложения.
- `DTO` — используется для передачи данных между клиентом и сервером.

Для работы с безопасностью настроены Spring Security, JWT-аутентификация и ролевая модель доступа. Изменения статусов заявок сохраняются отдельно, поэтому можно проследить историю их обработки.

## Статистика

Отдельный модуль аналитики написан на Kotlin. Он собирает данные о заявках за выбранный период и формирует сводный отчёт:

- Общее количество созданных заявок.
- Распределение по статусам и приоритетам.
- Количество просроченных открытых заявок.
- Среднее время решения заявок.

При обработке данных используются возможности Kotlin Collections API.

## Тестирование

Для проверки приложения используются JUnit 5 и Mockito.

Интеграционные тесты работают с PostgreSQL через Testcontainers. Благодаря этому можно проверять взаимодействие с реальной базой данных в изолированном Docker-контейнере, а не полагаться исключительно на моки.

Также проверяется загрузка Spring Application Context.

## Docker

Приложение и PostgreSQL запускаются через Docker Compose.

Dockerfile использует multi-stage сборку: сначала Gradle собирает приложение, затем готовый JAR переносится в отдельный образ на базе Java Runtime Environment 21.

### Запуск

Для запуска потребуется установленный Docker Engine и Docker Compose.

```bash
git clone https://github.com/ShamanNnNNn/pract_4_cource_technology_project.git
cd pract_4_cource_technology_project
docker compose up --build -d
```

Проверить состояние контейнеров можно командой:

```bash
docker compose ps
```

Остановить приложение:

```bash
docker compose down
```

Данные PostgreSQL хранятся в Docker volume, поэтому обычная остановка контейнеров не удаляет базу данных.

## API

После запуска Swagger UI доступен по адресу:

[http://localhost:8081/swagger-ui/index.html](http://localhost:8081/swagger-ui/index.html)

Через него можно посмотреть доступные endpoints и отправлять запросы к API.

Основные маршруты:

- `/api/applications` — работа с заявками.
- `/api/reports` — получение статистики.

## CI/CD

Для автоматизации сборки настроен GitHub Actions.

При push в `main` и создании Pull Request запускается pipeline из двух этапов:

**Verify**
- Сборка проекта.
- Запуск тестов.
- Формирование JAR-файла.

**Docker Build & Publish**
- Сборка Docker-образа.
- Публикация образа в GitHub Container Registry (GHCR).

В Registry публикуются два тега: `latest` и SHA коммита. Публикация выполняется при push в `main`, а для Pull Request проверяется только возможность сборки образа.
